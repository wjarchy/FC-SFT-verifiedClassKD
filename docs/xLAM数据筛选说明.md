## 为什么不能按数据卡示例直接读取

数据卡写的是每个参数带 `required` 布尔值，但实际 JSON 的 362,482 个参数都没有该字段。实际文件把可选性写进了类型字符串，例如：

- `str, optional`
- `int, optional`
- `List[int]`
- `Tuple[float, float]`
- `set`
- `Callable[[float], float]`

默认值也不可靠：64,099 个是空字符串，部分整数和布尔参数的默认值类型与声明类型不一致。

## 当前保守处理

- 类型字符串含 `optional`，或参数带默认字段：视为可选。
- 其余参数：视为必填。
- `str/int/float/bool` 转为标准 JSON 顶层类型。
- `List/Tuple/set` 只检查为数组；`Dict` 检查为对象。
- `set` 额外标记为无序数组。
- `Callable` 无法可靠表示为 JSON，包含它的整条数据剔除。
- xLAM 的默认值全部设为未知，不参加默认值等价判断。
- JSON Schema 联合类型使用 `integer|null` 等形式保存并逐成员检查。

这套规则偏保守：可能少认一些真实等价表达，但不会因为错误默认值制造假等价。

## BFCL 泄漏处理

固定官方 BFCL v4 仓库提交 `6ea57973c7a6097fd7c5915698c54c17c5b1b6c8`，扫描 7,053 条用户消息、4,763 个规范化不同问题。

xLAM 命中：

- 完全相同问题 3 条。
- 达到高相似阈值的问题共 102 个，全部来自 xLAM。
- 高相似阈值为 token Jaccard 至少 0.8，或字符序列相似度至少 0.9。
- ToolACE 完全相同和高相似命中均为 0。

删除按规范化问题文本执行，不只删除首次命中的行号。正式 3,250 条数据中 BFCL 命中残留为 0。

该方法不能数学上证明不存在任何语义泄漏，但已经覆盖完全重复和高表面相似模板。完整机器报告为 `reports/BFCL数据泄漏检查.json`。
